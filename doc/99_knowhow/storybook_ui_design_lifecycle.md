# Storybook を用いた画面設計ライフサイクル

| 項目 | 内容 |
|------|------|
| 対象 | コンポーネント指向 UI（React 等）の画面設計〜実装前レビュー |
| 粒度 | プロダクト非依存のノウハウ |
| 作成日 | 2026-07-26 |
| 更新日 | 2026-07-26 |

---

## 1. 目的

画面仕様を文章だけで固定せず、**実行可能な見た目**でレビューしてから本線実装に進む。  
正本は常に画面仕様（特に情報設計）に置き、Storybook はレビュー面・実装の種として使う。

---

## 2. 役割分担

| 成果物 | 置き場の原則 | 役割 |
|--------|--------------|------|
| 画面仕様 | ドキュメント領域（設計書） | **正本**。「何を載せるか / 載せないか / ゴール」 |
| ビジュアル方針・デザイントークン | 設計書またはデザインシステム | 配色・余白・フォント等 |
| Storybook（設定・Story） | **UI 実装パッケージと同じ場所** | **レビュー面**。本番と同系統のコンポーネント |
| 静的参考（任意） | ドキュメントの添付資産 | ワイヤ画像・下書き。実行コードではない |

**Storybook をドキュメント専用フォルダで管理しない。**  
ビルド・依存関係（バンドラ、コンポーネント、スタイル）は実装コードと同じツリーに寄せる。

---

## 3. 推奨ライフサイクル

```text
① 画面仕様（情報設計 → レイアウト → ビジュアル方針）
        ↓
② UI コンポーネント + Story（モックデータ / モック props）
        ↓
③ Storybook で状態別にレビュー
        ↓
④ 差分を画面仕様へ反映（正本を更新）
        ↓
⑤ 同じコンポーネントを本線（実データ・ユースケース接続）へ進める
```

### 各ステップの要点

| # | やること | 完了の目安 |
|---|----------|------------|
| ① | 各画面の役割・載せる要素・載せない要素・ゴールを書く | レビュー対象の情報設計が欠けない |
| ② | 画面 / パネル / 部品単位でコンポーネント化し、Story にモックを渡す | 仕様の構造と Story の階層が対応する |
| ③ | 空 / 読込中 / 成功 / エラー / プレースホルダなどを並べて確認 | 優先順・スコープ外が仕様どおり |
| ④ | 見た目で決まった配置・文言・状態を仕様に書き戻す | 仕様と Story が矛盾しない |
| ⑤ | モックを実データ取得に差し替え | Story は回帰・カタログとして残す |

画面設計は次の 3 層をこの順で固める。Storybook は主に **レイアウト以降の検証** と **状態の可視化** に使う。

| 層 | 決めること | 正本の置き場 |
|----|------------|--------------|
| 情報設計 | 何を載せるか、優先順位、載せないもの、ゴール | 画面仕様（人が握る） |
| レイアウト | どこに置くか、読む順序 | 仕様のワイヤ＋ Story |
| ビジュアル | 配色・フォント・余白・トーン | トークン / デザインシステム |

---

## 4. HTML モックとの関係

| 方針 | 中間物 | 使う場面 |
|------|--------|----------|
| **推奨** | 本番と同系統の UI + Storybook | 実装まで同じ資産を使いたい |
| 補助（任意） | 静的 HTML/CSS | レイアウトの超初期確認だけしたいとき |

HTML は **捨てる下書き** に留め、正本にも本線実装の種にもしない。  
生成 HTML の深いネストは採用せず、画面 → パネル → 部品の浅い構造に書き直す。

「仕様 → HTML 生成 → Storybook → 仕様修正」でも回るが、HTML → 本番 UI への二重作業が増えやすい。コンポーネント指向で実装するなら、**最初から同じスタック + Storybook** の方がトータルで安いことが多い。

---

## 5. 置き場（一般形）

```text
<repo>/
  <ui-app>/                 # Presentation / フロントの主戦場
    .storybook/             # Storybook 設定
    src/
      components/
      screens/              # または pages / features などプロジェクト慣習に従う
      **/*.stories.*        # コンポーネント隣でも stories/ でも可
  <docs>/
    <ui-spec>/              # 画面仕様・トークン方針
    knowhow/                # 本書のような横断ノウハウ
```

モノレポなら UI パッケージ配下、単一リポジトリならフロントルート配下に置く。いずれにせよ **「動く UI と同じ場所」** が原則。

---

## 6. Storybook が効きやすい条件

次のようなプロダクト・画面だと特に効果が高い。

- **同じ部品を複数画面で共用**する（一覧と詳細、単体と埋め込みなど）
- 段階リリースで **未実装領域をプレースホルダ** として見せる必要がある
- 表示は比較的単純で、**モック props / ViewModel** で状態を再現できる
- API 依存が薄い、または境界がはっきりしていてモックしやすい

逆に、画面全体が複雑なサーバー状態や認可に強く依存する場合は、Story の粒度を「ページ全体」より「パネル・部品」に落とすと破綻しにくい。

---

## 7. レビュー観点（固定する）

見た目の好みより、次をチェックする。

1. **載せる要素**の優先順が仕様どおりか（上から読めるか）
2. **載せない要素**（スコープ外）が出ていないか
3. **ゴール操作**が明確か（その画面で達成したい行動が一目で分かるか）
4. 状態（空・エラー・プレースホルダ）が「壊れた画面」に見えないか
5. グループ構造が浅いこと（画面 → パネル → 部品）

---

## 8. 先に用意する Story の目安

プロジェクト固有の画面名に依存せず、次の単位から揃える。

| 単位 | 主な状態例 |
|------|------------|
| アプリシェル（ナビ・ヘッダ） | 既定レイアウト |
| 主入力フォーム | 初期 / バリデーションエラー |
| 主結果ビュー（本実装相当） | 空 / 読込中 / 成功 / エラー |
| 共用パネル（複数画面で使う塊） | 単体表示 / 埋め込み表示 |
| 未実装枠 | プレースホルダ文言のみ |
| 破壊的・非同期操作 UI | 未実行 / 実行中 / 成功 / 失敗 |

---

## 9. やってはいけないこと

- Storybook をドキュメント専用ツリーだけで管理する（実装と乖離する）
- Story の見た目で仕様を上書きしたまま、画面仕様を更新しない
- 情報設計が固まらないうちにビジュアルだけ詰める
- HTML モックを本番コンポーネントの代わりに長く温存する
- ページ全体 Story だけを量産し、再利用部品の状態カタログを持たない

---

## 10. まとめ

- **正本**: 画面仕様の情報設計
- **レビュー面**: UI 実装と同じ場所にある Storybook
- **サイクル**: 仕様 → Story → レビュー → 仕様修正 → 本線接続
- HTML は任意の下書き。コンポーネント指向なら最初から同じスタック + Storybook を主戦場にする
